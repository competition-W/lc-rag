# RAG 文档处理服务

## 1. 项目概述

这是一个基于 LLM 和向量数据库的 RAG（Retrieval-Augmented Generation）文档处理服务，支持多部门文档管理、智能检索和生成式问答。

## 2. 核心架构

```
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│  FastAPI API    │────▶│  Celery 异步任务 │────▶│  文档处理流水线 │
└─────────────────┘     └─────────────────┘     └─────────────────┘
          ▲                         ▲                         │
          │                         │                         ▼
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│  MinIO 对象存储 │◀────│  Milvus 向量库  │◀────│  向量化模型     │
└─────────────────┘     └─────────────────┘     └─────────────────┘
```

## 3. 构建索引流程

### 3.1 文档上传流程

1. **API 调用**：客户端通过 `POST /documents/upload` 接口上传文件
2. **权限验证**：验证用户是否有权限上传到指定部门
3. **文件验证**：
   - 检查文件类型是否支持（基于 `settings.FILE_TYPE_MAPPING`）
   - 检查文件大小是否超过限制（`settings.MAX_FILE_SIZE`）
4. **生成存储路径**：`department/uuid.ext`
5. **上传 MinIO**：将原始文件存储到 MinIO 对象存储
6. **触发异步任务**：调用 Celery 任务 `process_document_task_async` 进行后续处理

### 3.2 文档处理流水线

```
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│  1. 从 MinIO 下载 │────▶│  2. 文档解析    │────▶│  3. 生成文档片段 │
└─────────────────┘     └─────────────────┘     └─────────────────┘
          ▲                         ▲                         │
          │                         │                         ▼
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│  8. 写入 Milvus │◀────│  7. 附加向量    │◀────│  6. 批量向量化   │
└─────────────────┘     └─────────────────┘     └─────────────────┘
          ▲                         │
          │                         ▼
          └─────────────────┐     ┌─────────────────┐
                            │     │  5. 转换为 TextNode │
                            └────▶└─────────────────┘
```

## 4. 表格文档解析

### 4.1 Excel 文档处理

#### 4.1.1 解析流程

1. **文件读取**：使用 `pandas.read_excel()` 读取 Excel 文件
2. **Schema 提取**：自动提取表格列名并转换为英文 Key
3. **逐行处理**：
   - 构建文本内容：`"列名: 值 | 列名: 值"` 格式
   - 构建元数据：使用转换后的英文 Key
   - 创建 TextNode 对象

#### 4.1.2 中英文列名映射

系统采用三级映射策略，确保所有列名都能正确转换为英文Key：

1. **预定义映射表（`COLUMN_MAPPING`）**：
   - 核心字段的固定映射
   - 确保关键过滤字段有准确的英文名称

   | 中文列名 | 英文映射 | 说明 |
   |---------|---------|------|
   | 物种 | species | 样本所属物种 |
   | 样本详细类型 | tissue | 样本组织类型 |
   | 实验平台 | platform | 实验所用平台 |
   | 样本大类 | category | 样本分类 |
   | 样本保存方案 | storage_method | 样本存储方式 |
   | 是否裂红 | is_lysis | 样本处理信息 |
   | 是否去死 | is_dead_removal | 样本处理信息 |
   | 核酸质量 | rin_score | 样本质量指标 |

2. **动态映射表**：
   - 自动生成并持久化存储的映射关系
   - 保存路径：`data/column_mapping.json`
   - 支持自动加载和更新

3. **自动拼音转换**：
   - 对新列名自动生成拼音映射
   - 策略：
     - 短列名使用完整拼音（如："新增列" -> "xin_zeng_lie"）
     - 长列名使用首字母缩写（如："中文列名测试" -> "zwlmcs"）
     - 自动添加配置的前缀（如：`col_`）

### 映射优先级

1. 优先使用**预定义映射表**
2. 其次使用**动态映射表**
3. 最后使用**自动拼音转换**

### 持久化存储

- 自动生成的映射会保存到 `data/column_mapping.json` 文件
- 服务重启后自动加载，保持映射一致性
- 支持手动编辑和扩展

#### 4.1.3 生成的 TextNode 结构

```python
TextNode(
    text="物种: 小鼠 | 组织: 肝脏 | 平台: Illumina",
    metadata={
        "department": "research",
        "uploader": "user123",
        "filename": "samples.xlsx",
        "doc_type": "excel",
        "sheet_name": "Sheet1",
        "row_index": 0,
        "species": "小鼠",
        "tissue": "肝脏",
        "platform": "Illumina",

```

## 5. 文档切片（Chunking）机制

### 5.1 切片策略

| 文档类型 | 切片策略 | 切片大小 |
|---------|---------|---------|
| Excel | 按行切片 | 每行1个chunk |
| PDF | 待实现 | 待配置 |
| Word | 待实现 | 待配置 |
| Markdown | 待实现 | 待配置 |

### 5.2 切片元数据

每个切片包含丰富的元数据，用于后续检索和过滤：

- 基础信息：部门、上传者、文件名、文档类型
- 文档特定信息：表名（Excel）、页码（PDF）、标题层级（Markdown）
- 业务字段：根据文档内容提取的结构化数据（如物种、组织、平台等）

## 6. 向量化实现

### 6.1 向量模型

系统使用阿里云通义千问的向量模型：

| 模型名称 | 类型 | 用途 |
|---------|------|------|
| text-embedding-v4 | 稠密向量 | 文本向量化（同步接口） |
| text-embedding-async-v4 | 稠密向量 | 文本向量化（异步批量接口） |

### 6.2 向量化流程

1. **文本提取**：从每个 TextNode 中提取文本内容
2. **批量向量化**：使用异步接口一次性提交所有文本
3. **向量附加**：将生成的向量附加到对应的 TextNode
4. **写入 Milvus**：将包含向量的 TextNode 写入向量数据库

### 6.3 性能优化

- 使用异步批量生成 Embeddings，减少 API 调用次数
- 跳过不需要向量化的元数据字段（通过 `excluded_embed_metadata_keys` 配置）
- 支持向量维度配置（`settings.MILVUS_EMBEDDING_DIM`）

## 7. MinIO 存储

### 7.1 存储内容

- **原始文档**：用户上传的原始文件
- **存储路径**：`department/uuid.ext`
- **Bucket 配置**：
  - `settings.MINIO_BUCKET_DOCUMENTS`：存储原始文档
  - `settings.MINIO_BUCKET_PROCESSED`：存储处理后的文档（预留）

### 7.2 客户端实现

- 单例模式设计，确保全局唯一客户端实例
- 支持预签名 URL 生成，用于临时访问文件
- 自动创建所需的 Bucket

## 8. Milvus 向量存储

### 8.1 存储结构

- **集合命名**：`dept_{department}`（按部门隔离数据）
- **向量索引**：
  - 索引类型：`IVF_FLAT`
  - 相似度度量：`COSINE`
  - 参数：`nlist: 1024`
- **向量维度**：由 `settings.MILVUS_EMBEDDING_DIM` 配置

### 8.2 存储内容

每个向量条目包含：

- **向量数据**：文本的稠密向量表示
- **文本内容**：原始文本片段
- **元数据**：用于过滤的结构化信息

### 8.3 数据隔离

- 按部门创建独立的集合
- 支持跨部门查询（需权限验证）
- 支持按部门列出可用集合

## 12. 检索流程与场景

### 12.1 检索核心流程

```
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│  1. 接收查询请求 │────▶│  2. 意图理解    │────▶│  3. 提取搜索词  │
└─────────────────┘     └─────────────────┘     └─────────────────┘
          │                         │                         ▼
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│  8. 返回结果    │◀────│  7. LLM生成回答 │◀────│  6. 挑选最佳结果 │
└─────────────────┘     └─────────────────┘     └─────────────────┘
          ▲                         ▲                         │
          │                         │                         ▼
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│  4. 选择检索策略 │◀────│  5. 执行检索    │◀────│  重排序(Rerank) │
└─────────────────┘     └─────────────────┘     └─────────────────┘
```

### 12.2 详细检索步骤

1. **查询请求接收**
   - 客户端通过 `POST /query` 接口发送请求
   - 请求包含：自然语言文本、是否使用LLM生成回答的标志

2. **意图理解与查询解析**
   - 调用 `parse_user_query` 函数，使用LLM将自然语言转换为结构化查询
   - 提取：
     - `real_query`：搜索关键词
     - `column_filters`：结构化过滤条件（如物种、组织、平台等）
   - 空搜索词兜底：如果提取的搜索词为空，回退使用用户原始提问

3. **统一检索服务**
   - 根据是否有过滤条件选择检索策略
   - 如果有过滤条件：走**结构化表格检索**
   - 如果没有过滤条件：走**通用语义检索**

4. **检索策略执行**

#### 4.1 结构化表格检索

```
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│  构建MetadataFilter│────▶│  初次检索      │────▶│  检查命中结果   │
└─────────────────┘     └─────────────────┘     └─────────────────┘
          │                         │                         │
          │                         │                         ▼
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│  返回结果       │◀────│  挑选best_rows  │◀────│  兜底策略执行   │
└─────────────────┘     └─────────────────┘     └─────────────────┘
```

- **构建过滤器**：包含部门隔离和用户筛选条件
- **初次检索**：使用搜索词和过滤器执行检索
- **兜底策略**：如果初次检索未命中，忽略关键词，仅按Filter检索
- **结果处理**：
  - 全部结果（`all_rows`）：用于前端展示，最多返回2000条
  - 最佳结果（`best_rows`）：用于LLM生成回答，数量由`llm_top_k`控制

#### 4.2 通用语义检索

```
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│  构建部门过滤   │────▶│  扩大范围检索   │────▶│  获取候选节点   │
└─────────────────┘     └─────────────────┘     └─────────────────┘
          │                         │                         ▼
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│  返回最佳结果   │◀────│  结果格式化     │◀────│  重排序(Rerank) │
└─────────────────┘     └─────────────────┘     └─────────────────┘
```

- **部门过滤**：仅使用部门作为过滤条件
- **扩大检索**：获取4倍于`semantic_top_k`的候选节点
- **重排序**：使用`gte-rerank-v2`模型对候选节点进行重排序
- **结果处理**：仅返回重排序后的最佳结果

5. **重排序(Rerank)机制**
   - 模型：`gte-rerank-v2`（通义千问）
   - 功能：对候选节点按相关性重新排序
   - 降级处理：如果Rerank失败，直接返回前N条节点

6. **LLM生成回答**
   - 使用检索到的`best_rows`作为上下文
   - 生成结构化回答：
     - **核心结论与分析**：直接回答用户问题，总结数据趋势
     - **支持数据详情**：列出支撑结论的具体数据
   - 模型：`qwen-plus`（通义千问）
   - 参数：
     - `max_tokens`: 2048
     - `temperature`: 0.3（降低随机性，保证事实准确）

### 12.3 检索场景与方式

| 场景 | 特征 | 检索策略 | 结果特点 |
|------|------|----------|----------|
| **自然语言问答** | 无明确过滤条件，如"帮我找心脏相关数据" | 通用语义检索 | 返回相关性排序的结果，适合生成式回答 |
| **精确条件过滤** | 有明确的过滤条件，如"列出小鼠肝脏的数据" | 结构化表格检索 | 返回符合所有条件的结果，适合数据浏览 |
| **混合检索** | 既有自然语言，又有过滤条件，如"帮我找小鼠心脏的单细胞数据" | 结构化表格检索 + 语义增强 | 先按条件过滤，再按语义排序，兼顾准确性和相关性 |
| **空搜索词** | 仅包含过滤条件，如"列出所有小鼠数据" | 结构化表格检索（兜底策略） | 忽略关键词，仅按过滤条件检索 |

### 12.4 检索优化机制

1. **空搜索词兜底**：防止向量检索报错
2. **检索失败降级**：当语义检索未命中时，触发兜底策略
3. **重排序降级**：当Rerank失败时，直接返回前N条结果
4. **Token优化**：
   - 限制Schema显示数量，防止Token溢出
   - 过滤无关字段，减少上下文长度
5. **批量处理**：设置合理的嵌入批量大小（100），平衡速度和API限制
